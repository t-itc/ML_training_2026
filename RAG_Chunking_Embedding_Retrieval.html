1 · Concept

Why chunking decides retrieval quality

Retrieval can only return what the index contains. If the right fact is split across two chunks, buried in a 3-page chunk about five topics, or cut off by the model's input limit, no retriever will find it cleanly. Chunking controls three things:

🎯 Precision of the vector

One vector summarises one chunk. A focused chunk gives a focused vector; a chunk mixing leave, expenses and IT gives an “average” vector that matches everything weakly.

🧩 Completeness of context

The chunk is also what the LLM reads. Too small and “18 days” loses “annual leave”; too large and prompts get long and noisy.

📏 Model limits

Embedding models truncate long input. all-MiniLM-L6-v2 stops at 256 tokens — text after that is silently ignored for the vector.

Characters are not tokens

Our simple splitters count characters. Models count tokens — sub-word pieces produced by the model's own tokenizer. Common English words are often one token; rare words, codes, numbers and non-English text split into several. As a rough rule of thumb for English, one token ≈ 4 characters, but the real ratio depends on the tokenizer and the text. Always measure with the model's tokenizer before trusting a limit:

from app.embeddings import EmbeddingModel

model = EmbeddingModel("minilm")

print(len(text), "characters")
print(count_tokens(text, model.tokenizer), "tokens (real tokenizer)")
print(count_tokens(text), "tokens (rough estimate: chars / 4)")
print(model.tokenizer.tokenize(text))      # see how codes split into pieces
⚠️
Silent truncation

A 2,000-character chunk may be ~500 tokens. MiniLM embeds only the first 256 tokens; the rest of the chunk is still sent to the LLM later, but it was never searchable. Size chunks in tokens against the model's limit (and leave room for any query/document prefix).

The seven strategies

Expand each strategy. Examples use the employee handbook from data/employee_handbook.md.

1Fixed-size chunkingsimplest baseline

Definition: cut the text every N characters (or tokens), ignoring its content.

How it works: a window of size N starts at 0, emits text[0:N], then jumps to N, 2N, …; the last chunk is shorter.

Step-by-step (N = 40):

Employees receive 18 days of annual paid leave per calendar year. → chunk 0: "Employees receive 18 days of annual paid" → chunk 1: " leave per calendar year." ← "leave" separated from "annual paid"
Advantages
  • Trivial, fast, predictable sizes
  • Easy to keep under a token limit
Limitations
  • Cuts words, sentences, facts
  • Ignores headings and topics
Use for
  • Baselines and quick prototypes
  • Unstructured logs or transcripts
2Fixed-size with overlapbaseline + safety margin

Definition: fixed-size windows where each chunk repeats the last O characters of the previous one.

How it works: the window moves by step = N − O instead of N. A fact cut at a boundary appears whole in the next chunk, as long as it is shorter than O.

N = 40, O = 15 → step 25 chunk 0: "Employees receive 18 days of annual paid" chunk 1: "s of annual paid leave per calendar year." ← overlap restores the phrase
Advantages
  • Fewer facts lost at boundaries
  • Still simple and predictable
Limitations
  • Duplicated text: more vectors, storage, cost
  • Duplicates may fill the top-K with near-identical chunks (→ MMR)
Use for
  • Default for unstructured prose
  • Typical overlap 10–20% of chunk size
3Sentence-based chunkingnever cut a sentence

Definition: split into sentences, then group consecutive sentences until a size limit is reached.

How it works: sentence splitter → add sentences to the current chunk while it fits → start a new chunk. Optional overlap repeats the last k sentences. A single sentence longer than the limit becomes its own chunk.

limit 120 chars chunk 0: "Employees receive 18 days of annual paid leave per calendar year. Up to five unused days may be carried over to the next year." (too long together? → split) chunk 0: "Employees receive 18 days of annual paid leave per calendar year." chunk 1: "Up to five unused days may be carried over to the next year. Leave requests must be submitted at least two weeks in advance."
Advantages
  • Each chunk is grammatical and readable
  • Good citation units
Limitations
  • Sentence splitting is hard (“e.g.”, “No. 5”, bullet lists)
  • Variable chunk lengths
  • Ignores topics across sentences
Use for
  • Policies, FAQs, articles
  • When answers are 1–3 sentences
4Recursive character chunkingthe practical default

Definition: try to split on the biggest natural boundary first and only fall back to smaller boundaries when a piece is still too large.

How it works: separators in priority order ["\n\n", "\n", ". ", " ", ""]. Split on paragraphs; any piece over the limit is split on lines; still too big → sentences → words → characters. Small neighbouring pieces are merged back up to the limit.

limit 200 "### 2.1 Annual Leave\nEmployees receive 18 days…\n\n### 2.2 Sick Leave\n…" 1. split on "\n\n" → section pieces (each ≤ 200? keep) 2. a 350-char piece → split on "\n" → heading line + paragraph 3. paragraph still 260 → split on ". " → sentences 4. merge neighbours while ≤ 200
Advantages
  • Respects paragraphs and sentences when possible
  • Guaranteed max size
  • Works on almost any text
Limitations
  • Still size-driven, not meaning-driven
  • Heading may end up separated from its body
Use for
  • Good general default
  • Mixed documents without reliable structure
5Semantic chunkingsplit where the topic changes

Definition: use embeddings to find topic shifts between neighbouring sentences and start a new chunk there.

How it works: embed every sentence → distance between neighbours = 1 − cosine → distances above a percentile (e.g. 80th) are boundaries → optional max length.

sentences: S1 leave S2 leave S3 leave S4 sick S5 sick neighbour distance: 0.21 0.18 0.55 0.20 80th percentile ≈ 0.40 → boundary between S3 and S4 (values illustrative)
Advantages
  • Chunks follow meaning, not character counts
  • Helps when structure is missing
Limitations
  • Embeds every sentence: slower, costs compute
  • Threshold needs tuning; results vary by model
  • Can create very short or long chunks
Use for
  • Transcripts, emails, long prose without headings
  • Worth testing when recursive splits look wrong
6Document-structure-based chunkingheadings, sections, tables

Definition: use the document's own structure — Markdown/HTML headings, PDF sections, numbered clauses, table rows — as chunk boundaries.

How it works: parse headings → one chunk per section → store the heading path as metadata (Employee Handbook > 2. Leave > 2.2 Sick Leave). Oversized sections are split further with a recursive splitter.

## 2. Leave ### 2.2 Sick Leave Employees are entitled to 10 days… → chunk: "Employees are entitled to 10 days…" metadata.section = "Employee Handbook > 2. Leave > 2.2 Sick Leave"
Advantages
  • Chunks match how authors organised knowledge
  • Heading path = free metadata for filtering and citations
Limitations
  • Needs reliable structure (PDF extraction often loses it)
  • Section sizes vary widely
Use for
  • Handbooks, manuals, contracts, wikis, API docs
7Parent-child chunkingsearch small, return big

Definition: store two levels: small child chunks for searching and large parent chunks for the LLM's context. Each child keeps its parent_id.

How it works: index children → a query matches a precise child → return its parent (deduplicated) to the LLM.

parent-3 "2.2 Sick Leave": "Employees are entitled to 10 days of paid sick leave per year. A medical certificate is required for absences longer than two consecutive days." child-4: "Employees are entitled to 10 days of paid sick leave per year." child-5: "A medical certificate is required for absences longer than two consecutive days." ← matches "doctor's note" → LLM receives parent-3 (both sentences)
Advantages
  • Precise matching and complete context
  • Reduces “answer cut in half” problems
Limitations
  • Two stores/levels to maintain
  • Parents can be long → more prompt tokens
Use for
  • Policies and manuals where facts need surrounding rules

4 · Workflow

Choosing and testing a chunking strategy

  1. Inspect the extracted text of a few documents: is there structure (headings, lists, tables)?
  2. Pick a baseline: structure-based if headings are reliable, otherwise recursive with ~10–20% overlap.
  3. Size in tokens under the embedding model's limit; leave room for prefixes.
  4. Attach metadata to every chunk: source, page/section, department, date.
  5. Evaluate retrieval (Module 5) and compare against one alternative strategy — change one thing at a time.

5 · Python implementation

app/chunking.py

Every function returns Chunk objects that remember their character offsets — needed for highlighting, citations and parent lookups.

@dataclass
class Chunk:
    id: str
    text: str
    start: int                       # character offset in the original text
    end: int                         # exclusive
    metadata: dict = field(default_factory=dict)

def split_sentences(text: str) -> list[tuple[int, int]]:
    """Return (start, end) offsets of sentences. Simple regex splitter:
    good enough for policies; use spaCy/nltk for abbreviations like 'e.g.'."""
    spans = []
    for m in _SENTENCE_RE.finditer(text):
        start, end = m.start(), m.end()
        while start < end and text[start].isspace():
            start += 1
        while end > start and text[end - 1].isspace():
            end -= 1
        if end > start:
            spans.append((start, end))
    return spans

Fixed-size and overlap — line by line

def fixed_size_chunks(text: str, chunk_size: int = 200, overlap: int = 0, prefix: str = "fx") -> list[Chunk]:
    _validate(chunk_size, overlap)
    chunks: list[Chunk] = []
    step = chunk_size - overlap            # how far the window moves each time
    start = 0
    while start < len(text):
        end = min(start + chunk_size, len(text))
        chunks.append(Chunk(f"{prefix}-{len(chunks)}", text[start:end], start, end))
        if end == len(text):
            break
        start += step
    return chunks

Sentence-based

def sentence_chunks(text: str, max_chars: int = 300, overlap_sentences: int = 0, prefix: str = "sn") -> list[Chunk]:
    """Group whole sentences until max_chars is reached. A single sentence
    longer than max_chars becomes its own chunk (sentences are never cut)."""
    if max_chars <= 0 or overlap_sentences < 0:
        raise ValueError("max_chars must be positive and overlap_sentences >= 0")
    sents = split_sentences(text)
    chunks: list[Chunk] = []
    i = 0
    while i < len(sents):
        j = i + 1
        while j < len(sents) and sents[j][1] - sents[i][0] <= max_chars:
            j += 1
        start, end = sents[i][0], sents[j - 1][1]
        chunks.append(Chunk(f"{prefix}-{len(chunks)}", text[start:end], start, end))
        if j >= len(sents):
            break
        i = max(i + 1, j - overlap_sentences)   # always move forward
    return chunks
  • split_sentences(text)Regex splitter returning offsets; fine for policies. For abbreviations and lists use spaCy or NLTK.
  • sents[j][1] - sents[i][0] <= max_charsKeep adding whole sentences while the span from the first sentence's start to the candidate's end fits.
  • i = max(i + 1, j - overlap_sentences)Next chunk starts k sentences back (overlap) but always moves forward — prevents infinite loops.

Recursive character chunking — line by line

def recursive_chunks(text: str, chunk_size: int = 300, overlap: int = 0,
                     separators: Sequence[str] = DEFAULT_SEPARATORS, prefix: str = "rc") -> list[Chunk]:
    """Split on the 'largest' separator first (paragraphs), and only fall back
    to smaller separators (lines, sentences, words, characters) for pieces that
    are still too long. Neighbouring small pieces are merged up to chunk_size."""
    _validate(chunk_size, overlap)

    def split(start: int, end: int, seps: Sequence[str]) -> list[tuple[int, int]]:
        if end - start <= chunk_size:
            return [(start, end)]
        sep, rest = seps[0], seps[1:]
        if sep == "":                                    # last resort: hard cut
            return [(s, min(s + chunk_size, end)) for s in range(start, end, chunk_size)]
        pieces, pos = [], start
        while True:
            idx = text.find(sep, pos, end)
            if idx == -1:
                pieces.append((pos, end))
                break
            pieces.append((pos, idx + len(sep)))          # keep the separator with the left piece
            pos = idx + len(sep)
        if len(pieces) == 1:                              # separator not present -> try smaller one
            return split(start, end, rest)
        out = []
        for a, b in pieces:
            out.extend(split(a, b, rest) if b - a > chunk_size else [(a, b)])
        return out

    # merge small neighbouring pieces up to chunk_size
    merged: list[tuple[int, int]] = []
    for a, b in split(0, len(text), list(separators)):
        if merged and b - merged[-1][0] <= chunk_size:
            merged[-1] = (merged[-1][0], b)
        else:
            merged.append((a, b))

    chunks = []
    for a, b in merged:
        a = max(0, a - overlap) if chunks else a          # optional character overlap
        piece = text[a:b]
        lead = len(piece) - len(piece.lstrip())
        trail = len(piece) - len(piece.rstrip())
        if piece.strip():
            chunks.append(Chunk(f"{prefix}-{len(chunks)}", piece.strip(), a + lead, b - trail))
    return chunks

Semantic chunking

def semantic_chunks(text: str, embed: Callable[[list[str]], np.ndarray],
                    breakpoint_percentile: float = 80.0, max_chars: int = 600, prefix: str = "sm") -> list[Chunk]:
    """Start a new chunk where the meaning changes.

    1. split into sentences
    2. embed every sentence (``embed`` returns L2-normalised vectors)
    3. distance between neighbours = 1 - cosine similarity
    4. distances above the given percentile are 'topic shifts' -> boundaries
    """
    sents = split_sentences(text)
    if len(sents) <= 1:
        return [Chunk(f"{prefix}-0", text.strip(), 0, len(text))] if text.strip() else []
    vecs = embed([text[a:b] for a, b in sents])
    distances = 1.0 - np.sum(vecs[:-1] * vecs[1:], axis=1)       # one per neighbour pair
    threshold = np.percentile(distances, breakpoint_percentile)

    chunks, group_start = [], 0
    for i in range(1, len(sents)):
        too_long = sents[i][1] - sents[group_start][0] > max_chars
        if distances[i - 1] > threshold or too_long:
            a, b = sents[group_start][0], sents[i - 1][1]
            chunks.append(Chunk(f"{prefix}-{len(chunks)}", text[a:b], a, b,
                                {"split_distance": round(float(distances[i - 1]), 3)}))
            group_start = i
    a, b = sents[group_start][0], sents[-1][1]
    chunks.append(Chunk(f"{prefix}-{len(chunks)}", text[a:b], a, b))
    return chunks

Structure-based and parent-child

def markdown_section_chunks(markdown: str, prefix: str = "md") -> list[Chunk]:
    """One chunk per section; the heading path is kept as metadata
    (e.g. 'Employee Handbook > Leave > Sick Leave')."""
    heads = list(_HEADING_RE.finditer(markdown))
    chunks, path = [], []
    for k, h in enumerate(heads):
        level, title = len(h.group(1)), h.group(2).strip()
        path = path[: level - 1] + [title]
        body_start = h.end()
        body_end = heads[k + 1].start() if k + 1 < len(heads) else len(markdown)
        body = markdown[body_start:body_end]
        if body.strip():
            lead = len(body) - len(body.lstrip())
            a = body_start + lead
            b = a + len(body.strip())
            chunks.append(Chunk(f"{prefix}-{len(chunks)}", markdown[a:b], a, b,
                                {"section": " > ".join(path), "level": level}))
    return chunks


def parent_child_chunks(markdown: str, child_max_chars: int = 160) -> tuple[list[Chunk], list[Chunk]]:
    """Parents = whole sections (rich context for the LLM).
    Children = small sentence groups inside each parent (precise for search).
    Each child stores ``parent_id`` so a child hit can be swapped for its parent."""
    parents = markdown_section_chunks(markdown, prefix="parent")
    children: list[Chunk] = []
    for p in parents:
        for c in sentence_chunks(p.text, max_chars=child_max_chars, prefix="tmp"):
            children.append(Chunk(f"child-{len(children)}", c.text, p.start + c.start, p.start + c.end,
                                  {"parent_id": p.id, "section": p.metadata["section"]}))
    return parents, children
  • path = path[: level - 1] + [title]Maintains the heading trail: a level-3 heading replaces everything from level 3 down.
  • {"section": " > ".join(path)}Heading path stored as metadata — usable for filtering and for citations.
  • parents = markdown_section_chunks(...)Parents are whole sections.
  • "parent_id": p.idEach child points to its parent; ParentChildRetriever (Module 3) uses this to swap child hits for parents.

1 · Concept

From text to vectors

An embedding is a fixed-length list of numbers produced by a neural network (usually a Transformer encoder) so that texts with similar meaning get vectors pointing in similar directions. The same model must embed the documents (offline) and the query (online).

⏱️ Latency

Local models: cost is your CPU/GPU time; small models embed thousands of short chunks per minute on CPU. APIs: add network round-trips per query, but no hardware to run.

💰 Cost

Indexing cost scales with corpus tokens and every re-index. Query cost scales with traffic. Storage scales with n_chunks × dimensions × bytes.

🔐 Governance

API embeddings send document text to a third party. For confidential data clients often require local models or a private cloud deployment.

class EmbeddingModel:
    """Wraps a sentence-transformers model with the right prefixes and L2 normalisation."""

    def __init__(self, key: str = "minilm"):
        if key not in MODEL_CONFIGS:
            raise ValueError(f"Unknown model '{key}'. Choose from: {', '.join(MODEL_CONFIGS)}")
        from sentence_transformers import SentenceTransformer   # imported lazily (heavy)

        cfg = MODEL_CONFIGS[key]
        self.key, self.name = key, cfg["name"]
        self.query_prefix, self.doc_prefix = cfg["query_prefix"], cfg["doc_prefix"]
        try:
            self.model = SentenceTransformer(cfg["name"], trust_remote_code=cfg.get("trust_remote_code", False))
        except Exception as exc:
            raise RuntimeError(f"Could not load {cfg['name']}: {exc}. "
                               "The first run needs internet access to download the model.") from exc

    @property
    def dimension(self) -> int:
        return self.model.get_sentence_embedding_dimension()

    @property
    def tokenizer(self):
        return self.model.tokenizer

    def _encode(self, texts: list[str]) -> np.ndarray:
        vecs = self.model.encode(texts, normalize_embeddings=True, convert_to_numpy=True,
                                 batch_size=32, show_progress_bar=False)
        return np.asarray(vecs, dtype=np.float32)

    def encode_documents(self, texts: list[str]) -> np.ndarray:
        return self._encode([self.doc_prefix + t for t in texts])

    def encode_queries(self, texts: list[str]) -> np.ndarray:
        return self._encode([self.query_prefix + t for t in texts])
def cosine_similarity(a: np.ndarray, b: np.ndarray) -> np.ndarray:
    """Cosine similarity between rows of ``a`` (n, d) and ``b`` (m, d) -> (n, m).
    Works for un-normalised vectors too."""
    a = np.atleast_2d(a).astype(np.float32)
    b = np.atleast_2d(b).astype(np.float32)
    a_n = a / np.clip(np.linalg.norm(a, axis=1, keepdims=True), 1e-12, None)
    b_n = b / np.clip(np.linalg.norm(b, axis=1, keepdims=True), 1e-12, None)
    return a_n @ b_n.T

1 · Concept

Ten retrieval techniques

Retrieval = given a query, return a ranked list of chunks. The methods below differ in how they score (meaning vs words), what they search (all chunks, a filtered subset, small children) and how they assemble the final list (fusion, diversity).

1Dense vector retrievalmeaning

Concept: embed query and chunks with a bi-encoder; rank by cosine similarity.

Architecture: embedding model + vector index (NumPy matrix today; FAISS, pgvector, Qdrant, Weaviate, Milvus, Azure AI Search… in production, usually with approximate nearest-neighbour indexes such as HNSW).

Workflow: encode query → similarity against all (or ANN-selected) vectors → top-K.

Advantages
  • Synonyms, paraphrases, cross-lingual
Limitations
  • Exact codes, names, numbers
  • Needs a model and vectors
Applications
  • Natural-language Q&A over policies, KBs
2Sparse retrievalwords

Concept: represent texts by the terms they contain (vocabulary-sized, mostly-zero vectors) and score by term overlap, weighting rare terms higher.

Architecture: tokenizer + inverted index (term → list of documents), e.g. Elasticsearch/OpenSearch, Lucene, or rank_bm25 in memory.

Workflow: tokenise query → look up postings → score documents containing the terms → top-K.

Advantages
  • Exact matches, explainable, no GPU, mature tooling
Limitations
  • Vocabulary mismatch (“vacation” ≠ “leave”)
  • Needs language-aware tokenising/stemming
Applications
  • Error codes, SKUs, legal citations, names
3TF-IDFclassic sparse weighting

Concept: term weight = term frequency in the chunk × inverse document frequency (rare across the corpus → higher). Score = cosine between TF-IDF vectors.

Workflow: fit vocabulary + IDF on the corpus → transform query → cosine with every chunk vector.

Advantages
  • Simple, fast, built into scikit-learn
Limitations
  • Repeated terms keep adding weight; no length normalisation tuned for retrieval
Applications
  • Baselines, small collections, feature engineering
4BM25the sparse workhorse

Concept: a refinement of TF-IDF used by most search engines: term frequency saturates (the 10th “leave” adds little) and long documents are normalised.

score(D, Q) = Σ over query terms t: IDF(t) · tf(t,D)·(k1+1) / ( tf(t,D) + k1·(1 − b + b·|D|/avgdl) ) k1 ≈ 1.2–2.0 controls saturation b ≈ 0.75 controls length normalisation
Advantages
  • Strong, robust baseline; exact terms; explainable
Limitations
  • No semantics; scores unbounded (not comparable with cosine)
Applications
  • Keyword-heavy queries; first stage of hybrid search
5Hybrid retrievaldense + sparse

Concept: run dense and sparse retrieval and merge the lists, so each covers the other's blind spots.

Architecture: two indexes (or one engine supporting both) + a fusion step: Reciprocal Rank Fusion (ranks only) or weighted score fusion (needs score normalisation).

Advantages
  • Handles both paraphrases and exact codes
Limitations
  • Two indexes to maintain; fusion parameters to tune
Applications
  • Enterprise search with mixed query types — a common production default
6Metadata filteringrestrict the search space

Concept: only consider chunks whose metadata matches conditions (department, document type, date, region, access rights).

Workflow: pre-filter (filter, then rank — guarantees K matching results) or post-filter (rank, then drop — may return fewer than K).

Advantages
  • Precision, freshness, access control
Limitations
  • Only as good as the metadata; wrong filter hides the answer
Applications
  • “Only current HR policies for Germany”, per-user document permissions
7Maximum Marginal Relevance (MMR)relevant and diverse

Concept: pick results one at a time, rewarding relevance to the query and penalising similarity to results already picked.

MMR(d) = λ · sim(query, d) − (1 − λ) · max over selected s of sim(d, s) λ = 1 → plain top-K λ = 0 → maximum diversity typical λ ≈ 0.5–0.7
Advantages
  • Avoids top-K full of near-duplicates (overlap chunks, copies)
  • Covers several aspects of broad questions
Limitations
  • Can push out a second relevant chunk; λ needs tuning
Applications
  • Broad questions, duplicated document sets, summaries
8Parent-child retrievalmatch small, return big

Concept: search child chunks; return their parent sections (deduplicated). Uses the parent-child chunking from Module 1.

Advantages
  • Precise matching + full context
Limitations
  • Longer prompts; parent store to maintain
Applications
  • Policies, contracts, manuals
9Multi-query retrievalask several ways

Concept: generate several rephrasings of the question (usually with an LLM), retrieve for each, fuse the rankings (RRF).

"Am I allowed to accept a present from a vendor?" → "Can employees accept gifts from suppliers?" → "What is the rule for gifts from business partners?" → "Is there a limit on vendor gifts?" retrieve each → fuse with RRF
Advantages
  • Bridges vocabulary gaps; more robust recall
Limitations
  • Extra LLM call + N searches: latency and cost
  • Bad rewrites can drift off-topic
Applications
  • Short, ambiguous or colloquial questions
10Contextual retrievalgive each chunk its context

Concept: before indexing, prepend a short, document-aware context to every chunk (e.g. “From the 2026 HR Leave Policy, section on sick leave:”) — written by an LLM or built from metadata/heading paths — then embed and BM25-index the contextualised text.

Why: chunks like “This applies to all employees from 1 March.” are meaningless alone; the added context makes them retrievable. Structure-based heading paths (Module 1) are a cheap, deterministic version.

Advantages
  • Better retrieval for chunks that depend on surrounding text
Limitations
  • LLM call per chunk at indexing time (cost, time); must re-run when documents change
Applications
  • Long reports, contracts, financial filings with many cross-references

def matches_filters(doc: dict, filters: dict | None) -> bool:
    """filters = {"department": "HR"} or {"department": ["HR", "IT"], "doc_type": "policy"}."""
    if not filters:
        return True
    for key, allowed in filters.items():
        allowed = allowed if isinstance(allowed, (list, tuple, set)) else [allowed]
        if doc.get(key) not in allowed:
            return False
    return True
class DenseRetriever:
    """Embeds every document once (indexing), then answers queries with
    cosine similarity. ``model`` needs encode_documents() and encode_queries()
    returning L2-normalised vectors (see embeddings.EmbeddingModel)."""

    def __init__(self, docs: list[dict], model, text_key: str = "text"):
        if not docs:
            raise ValueError("No documents to index")
        self.docs, self.model = docs, model
        self.embeddings = model.encode_documents([d[text_key] for d in docs])   # (n_docs, dim)

    def search(self, query: str, top_k: int = 5, filters: dict | None = None) -> list[Result]:
        if not query.strip():
            raise ValueError("Query must not be empty")
        q = self.model.encode_queries([query])[0]                # (dim,)
        scores = self.embeddings @ q                             # cosine (vectors are normalised)
        allowed = np.array([matches_filters(d, filters) for d in self.docs])
        scores = np.where(allowed, scores, -np.inf)              # pre-filter: excluded docs can't win
        order = np.argsort(-scores)[:top_k]
        return [Result(self.docs[i], float(scores[i]), "dense") for i in order if np.isfinite(scores[i])]

B · Sparse retrieval: BM25 and TF-IDF

def tokenize(text: str) -> list[str]:
    """Lowercase words and numbers; 'VPN-417' -> ['vpn', '417']. No stemming,
    so 'working' and 'work' are different tokens (a classic BM25 limitation)."""
    return [t for t in re.findall(r"[a-z0-9]+", text.lower()) if t not in STOPWORDS]


class BM25Retriever:
    def __init__(self, docs: list[dict], text_key: str = "text", k1: float = 1.5, b: float = 0.75):
        self.docs = docs
        self.corpus_tokens = [tokenize(d[text_key]) for d in docs]
        self.bm25 = BM25Okapi(self.corpus_tokens, k1=k1, b=b)

    def search(self, query: str, top_k: int = 5, filters: dict | None = None) -> list[Result]:
        scores = self.bm25.get_scores(tokenize(query))
        allowed = np.array([matches_filters(d, filters) for d in self.docs])
        scores = np.where(allowed, scores, -np.inf)
        order = np.argsort(-scores, kind="stable")[:top_k]
        # documents with score 0 share no query term - BM25 has no evidence for them
        return [Result(self.docs[i], float(scores[i]), "bm25") for i in order if scores[i] > 0]


class TfidfRetriever:
    def __init__(self, docs: list[dict], text_key: str = "text"):
        self.docs = docs
        self.vectorizer = TfidfVectorizer(tokenizer=tokenize, lowercase=False, token_pattern=None)
        self.matrix = self.vectorizer.fit_transform([d[text_key] for d in docs])    # sparse (n_docs, vocab)

    def search(self, query: str, top_k: int = 5, filters: dict | None = None) -> list[Result]:
        q = self.vectorizer.transform([query])
        scores = (self.matrix @ q.T).toarray().ravel()           # rows are L2-normalised -> cosine
        allowed = np.array([matches_filters(d, filters) for d in self.docs])
        scores = np.where(allowed, scores, -np.inf)
        order = np.argsort(-scores, kind="stable")[:top_k]
        return [Result(self.docs[i], float(scores[i]), "tfidf") for i in order if scores[i] > 0]

D · MMR — line by line

def mmr(query_vec: np.ndarray, doc_vecs: np.ndarray, top_k: int = 4, lambda_mult: float = 0.5,
        candidate_ids: list[int] | None = None) -> list[int]:
    """Greedy MMR over normalised vectors.

    score(d) = lambda * sim(query, d) - (1 - lambda) * max sim(d, already selected)

    lambda_mult = 1.0 -> pure relevance (same as plain top-k)
    lambda_mult = 0.0 -> pure diversity
    Returns indices into doc_vecs, in selection order.
    """
    if not 0.0 <= lambda_mult <= 1.0:
        raise ValueError("lambda_mult must be between 0 and 1")
    candidates = list(range(len(doc_vecs))) if candidate_ids is None else list(candidate_ids)
    relevance = doc_vecs @ query_vec                         # sim(query, d) for every doc
    selected: list[int] = []
    while candidates and len(selected) < top_k:
        if selected:
            redundancy = np.max(doc_vecs[candidates] @ doc_vecs[selected].T, axis=1)
        else:
            redundancy = np.zeros(len(candidates))
        scores = lambda_mult * relevance[candidates] - (1 - lambda_mult) * redundancy
        best = candidates[int(np.argmax(scores))]
        selected.append(best)
        candidates.remove(best)
    return selected

def generate_query_variants(question: str, n: int = 3, model: str | None = None) -> list[str]:
    """Ask a local Ollama LLM for n rephrasings of the question.
    Returns [] if Ollama is not available, so callers can fall back."""
    model = model or os.getenv("OLLAMA_MODEL", "mistral")
    try:
        import ollama
        prompt = (f"Rewrite the following question in {n} different ways using different words "
                  f"(synonyms, formal and informal wording). Return one question per line, no numbering.\n\n"
                  f"Question: {question}")
        reply = ollama.chat(model=model, messages=[{"role": "user", "content": prompt}],
                            options={"temperature": 0.3})
        lines = [l.strip(" -*0123456789.").strip() for l in reply.message.content.splitlines()]
        return [l for l in lines if l.endswith("?") or len(l.split()) > 3][:n]
    except Exception as exc:                       # no ollama package / server / model
        print(f"[multi-query] Ollama unavailable ({exc}); using the original question only.")
        return []


def multi_query_search(retriever, question: str, variants: list[str], top_k: int = 5,
                       per_query_k: int = 10, k: int = 60) -> tuple[list[Result], dict[str, list[str]]]:
    """Retrieve for the original question AND each variant, then fuse with RRF.
    Returns (fused results, per-query rankings) so the effect can be shown."""
    queries = [question] + [v for v in variants if v.strip() and v != question]
    per_query = {q: [r.id for r in retriever.search(q, per_query_k)] for q in queries}
    fused = reciprocal_rank_fusion(list(per_query.values()), k=k)
    by_id = {d["id"]: d for d in retriever.docs}
    return [Result(by_id[i], s, "multi-query") for i, s in fused[:top_k]], per_query

class ParentChildRetriever:
    """Search small CHILD chunks (precise match), return their PARENT sections
    (complete context). Several children of one parent count once."""

    def __init__(self, parents, children, model):
        self.parents = {p.id: p for p in parents}
        self.children = children
        self.model = model
        self.child_vecs = model.encode_documents([c.text for c in children])

    def search(self, query: str, top_k: int = 2) -> list[tuple[object, object, float]]:
        q = self.model.encode_queries([query])[0]
        scores = self.child_vecs @ q
        results, seen = [], set()
        for i in np.argsort(-scores):
            child = self.children[i]
            pid = child.metadata["parent_id"]
            if pid in seen:
                continue
            seen.add(pid)
            results.append((self.parents[pid], child, float(scores[i])))   # (parent, matched child, score)
            if len(results) == top_k:
                break
        return results

Formula

RRF(d) = Σr ∈ rankings 1 / (k + rankr(d))

rank starts at 1; a document missing from a ranking adds nothing for that ranking; k (commonly 60) flattens the gap between rank 1 and rank 2. RRF uses positions only, so cosine scores (≈ 0–1) and BM25 scores (0–15+) never need to be put on the same scale.

      Reranking: bi-encoder vs cross-encoder

      Bi-encoder (first stage)

      Query and document are embedded separately; document vectors are computed once at indexing time. Searching millions of vectors takes milliseconds. The model never sees query and document together, so subtle relevance is approximated.

      Cross-encoder (reranker)

      Reads [query, document] together through one Transformer and outputs one relevance score. Captures word-by-word interactions — usually more accurate — but must run once per candidate per query, so it only reranks a short list (e.g. top 20–50).

      We use cross-encoder/ms-marco-MiniLM-L-6-v2, trained on the MS MARCO passage-ranking dataset (English web questions). Its outputs are unbounded relevance scores (logits): higher is more relevant; compare them only within one query.

      🎯
      When reranking helps — and when it cannot

      Reranking is useful when the first stage already returns the relevant candidates but in the wrong order. It cannot recover a document that was never retrieved — so retrieve generously (higher candidate K, hybrid) and rerank down to the final K.

      3 · Architecture

      Two-stage retrieval

      Stage 1 is fast and broad (recall). Stage 2 is slow and precise (ranking).
      4 · Workflow

      Rerank step by step

      1. Retrieve a generous candidate set with hybrid search (e.g. top 20–50).
      2. Form (query, candidate_text) pairs.
      3. Score all pairs with the cross-encoder (batch them).
      4. Sort by the new score; keep the final top-K for the LLM.
      5. Measure the latency budget: reranking time grows with the number of candidates.

      def reciprocal_rank_fusion(rankings: list[list[str]], k: int = 60) -> list[tuple[str, float]]:
    """RRF(d) = sum over rankings of 1 / (k + rank(d)), rank starting at 1.

    Uses only RANK positions, never raw scores, so it can merge rankers whose
    scores are on different scales (cosine 0-1 vs BM25 0-15+). k dampens the
    advantage of the very top positions; 60 is the value from the original paper.
    """
    fused: dict[str, float] = defaultdict(float)
    for ranking in rankings:
        for rank, doc_id in enumerate(ranking, start=1):
            fused[doc_id] += 1.0 / (k + rank)
    return sorted(fused.items(), key=lambda kv: (-kv[1], kv[0]))


class HybridRetriever:
    """Run dense and BM25 retrieval, then fuse their rankings with RRF."""

    def __init__(self, dense, sparse, candidates: int = 10, k: int = 60):
        self.dense, self.sparse = dense, sparse
        self.candidates, self.k = candidates, k
        self.by_id = {d["id"]: d for d in dense.docs}

    def search(self, query: str, top_k: int = 5, filters: dict | None = None) -> list[Result]:
        dense_ids = [r.id for r in self.dense.search(query, self.candidates, filters)]
        sparse_ids = [r.id for r in self.sparse.search(query, self.candidates, filters)]
        fused = reciprocal_rank_fusion([dense_ids, sparse_ids], k=self.k)
        return [Result(self.by_id[i], s, "hybrid-rrf") for i, s in fused[:top_k]]
      class Reranker:
    """A cross-encoder reads (query, document) TOGETHER and outputs one relevance
    score. More accurate than comparing two separate embeddings, but it must run
    once per candidate at query time - so only rerank a short candidate list."""

    def __init__(self, model_name: str = DEFAULT_RERANKER):
        from sentence_transformers import CrossEncoder       # lazy import (heavy)
        try:
            self.model = CrossEncoder(model_name)
        except Exception as exc:
            raise RuntimeError(f"Could not load {model_name}: {exc}. "
                               "The first run needs internet access to download the model.") from exc

    def rerank(self, query: str, candidates: list[Result], top_k: int | None = None) -> list[Result]:
        if not candidates:
            return []
        pairs = [(query, r.doc["text"]) for r in candidates]
        scores = self.model.predict(pairs)        # raw relevance scores (logits), higher = more relevant
        reranked = sorted(zip(candidates, scores), key=lambda x: -float(x[1]))
        out = [Result(r.doc, float(s), "rerank") for r, s in reranked]
        return out[:top_k] if top_k else out

      1 · Concept

      Four retrieval metrics

      We judge a retriever by comparing its ranked list with labelled relevant documents for each test question (binary relevance: relevant or not).

      MetricQuestion it answersFormula (per question)
      Precision@KHow much of what I return is relevant?relevant in top-K ÷ K
      Recall@KHow much of what is relevant did I return?relevant in top-K ÷ all relevant
      MRR (Mean Reciprocal Rank)How high is the first relevant result?1 ÷ rank of first relevant (0 if none), averaged over questions
      nDCG@KAre relevant results near the top?DCG = Σ reli / log₂(i + 1); divided by the best possible DCG
      🧭
      Which metric matters for RAG?

      The LLM only sees the top-K chunks, so Recall@K (is the evidence in the prompt at all?) is usually the first metric to watch; MRR/nDCG matter when K is small or the LLM pays more attention to the first chunks. Precision@K is capped when a question has fewer relevant documents than K (one relevant document → P@3 ≤ 0.33).

      def precision_at_k(retrieved: list[str], relevant: set[str], k: int) -> float:
    """Share of the top-k results that are relevant."""
    top = retrieved[:k]
    return sum(1 for d in top if d in relevant) / k


def recall_at_k(retrieved: list[str], relevant: set[str], k: int) -> float:
    """Share of all relevant documents that appear in the top-k."""
    if not relevant:
        return 0.0
    return sum(1 for d in retrieved[:k] if d in relevant) / len(relevant)


def reciprocal_rank(retrieved: list[str], relevant: set[str]) -> float:
    """1 / position of the FIRST relevant result (0 if none). Averaged -> MRR."""
    for pos, d in enumerate(retrieved, start=1):
        if d in relevant:
            return 1.0 / pos
    return 0.0


def ndcg_at_k(retrieved: list[str], relevant: set[str], k: int) -> float:
    """Normalised Discounted Cumulative Gain: rewards relevant results more
    the higher they are ranked. 1.0 = all relevant docs at the very top."""
    dcg = sum(1.0 / math.log2(pos + 1) for pos, d in enumerate(retrieved[:k], start=1) if d in relevant)
    ideal_hits = min(len(relevant), k)
    idcg = sum(1.0 / math.log2(pos + 1) for pos in range(1, ideal_hits + 1))
    return dcg / idcg if idcg else 0.0
      def evaluate(search: Callable[[str, int], list[str]], questions: list[dict], k: int = 3) -> dict:
    """search(question, k) must return a ranked list of document IDs."""
    rows = []
    for q in questions:
        retrieved = search(q["question"], k)
        relevant = set(q["relevant_ids"])
        rows.append({
            "id": q["id"], "question": q["question"], "relevant": sorted(relevant), "retrieved": retrieved,
            "precision": precision_at_k(retrieved, relevant, k),
            "recall": recall_at_k(retrieved, relevant, k),
            "rr": reciprocal_rank(retrieved, relevant),
            "ndcg": ndcg_at_k(retrieved, relevant, k),
        })
    n = len(rows) or 1
    summary = {m: sum(r[m] for r in rows) / n for m in ("precision", "recall", "rr", "ndcg")}
    return {"k": k, "rows": rows, "summary": summary}
