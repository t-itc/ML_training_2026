Module 1 · Concepts

Introduction to AI Agents and Agentic AI

⏱ 15 min

An LLM on its own is a function: text in, text out. It cannot check today's date, multiply exactly, read your database or remember yesterday. An agent wraps the LLM in a loop that gives it tools, state and memory, and lets the LLM decide what to do next.

1.1

Understanding AI agents

🧾 LLM application

  • You write the control flow: retrieve → prompt → answer.
  • One model call per request (or a fixed chain).
  • The LLM only generates text.
  • Predictable, cheap, easy to test.

Example: the RAG assistant from earlier sessions.

🤖 AI agent

  • The LLM decides the next step: answer, or call a tool and with what arguments.
  • Loops until the task is done (several model calls).
  • Acts through tools and observes the results.
  • More flexible, but less predictable and more expensive.

Example: Aria choosing the calculator and the date tool for one question.

What makes an application agentic?

🎯
Goal

It works toward the user's request, not through a fixed script.

🔀
Decides control flow

The LLM picks the next action. This is the key property.

🛠️
Acts with tools

Calls functions and APIs and reads their results.

🧠
Has state & memory

Keeps context within a task and across sessions.

How an agent makes decisions: reason → act → observe

Modern agents use the ReAct pattern through native tool calling:

Fixed chainRouterTool-calling agentAutonomous agent

🔑
Autonomous agents vs workflow-based applications

Use a workflow when the steps are known in advance (most RAG and ETL tasks). Use an agent when the steps depend on the request. Today we build a single tool-calling agent, the third position on the dial. It is the most common pattern in production.

The model's internal reasoning (its "chain of thought") is not necessarily exposed, and when a model does print reasoning text it is not a guaranteed record of how it decided. Module 2 · LangChain

LangChain Fundamentals and Your First Agent

⏱ 30 min

LangChain gives you standard building blocks (models, messages, tools) and one function, create_agent, that wires them into the agent loop from Module 1. Underneath, that loop runs on LangGraph.

2.1

Introduction to LangChain

LangChain is an open-source framework for building LLM applications and agents. It provides one interface for many model providers and the agent loop, so you write the logic once and can switch models later.

🧠

Models

ChatOllama, ChatOpenAI, init_chat_model("openai:gpt-4.1-mini"). Same .invoke() for every provider.

💬

Messages

SystemMessage, HumanMessage, AIMessage (may carry tool_calls), ToolMessage.

📝

Prompts

The system_prompt of the agent, or a dynamic prompt rebuilt each call by middleware (Module 4.5).

🛠️

Tools

Python functions decorated with @tool. Name, docstring and type hints become a JSON schema.

🤖

Agents

create_agent(model, tools, system_prompt, checkpointer, store, middleware).

🧅

Middleware

Hooks around the loop: @before_model, @dynamic_prompt, @wrap_tool_call, @after_agent.

LangChain and LangGraph

LangGraph is the lower-level runtime: a graph of nodes and edges with shared state, plus checkpointers (short-term memory), a Store (long-term memory), streaming and human-in-the-loop. create_agent builds a LangGraph graph for you. Because it is a LangGraph graph, it already supports persistence.

LangChain (langchain)LangGraph (langgraph)
LevelHigh-level: components and a ready-made agentLow-level: orchestration runtime
You writecreate_agent(...), tools, middlewareNodes, edges, state schema, conditional routing
Best forSingle agents with tools (today)Custom workflows, multi-agent systems, complex control flow
MemoryPass checkpointer= / store= to create_agentProvides InMemorySaver, SqliteSaver, InMemoryStore, SqliteStore, Postgres…
Relationshipcreate_agent() returns a compiled LangGraph StateGraph, so .invoke(), .stream() and .get_state() all work.

How does tool calling work with LLMs?

Each tool becomes a JSON schema (name, description, parameters). The provider API gets these schemas, and models trained for function calling reply with a structured call instead of text. The LLM never runs code. Your process does.

What happens when a tool fails?

If the tool returns an error string, the model reads it and can recover. If it raises, the run stops unless middleware catches the error and turns it into a ToolMessage (Module 3.5).

Module 3 · Tools

Tools Integration with LangChain

⏱ 30 min

Tools turn a talking model into an agent that can act. A tool is a Python function plus a description that the LLM reads. The description is effectively a prompt: if it is vague, the agent will pick the wrong tool.

3.1

Understanding tools

LLM limitationWhyTool in Aria
Exact arithmeticModels predict tokens; they do not computecalculator
Today's date and timeNo clock; knowledge stops at the training cut-offget_current_datetime
Live dataNo internet access at inference timeget_weather (sample data or Open-Meteo)
Private knowledgeNever saw your company documentssearch_knowledge (RAG-style search)

Built-in tools

Integrations in langchain-community and partner packages: web search (Tavily), Wikipedia, SQL toolkits, file system, provider-hosted tools. Quick to add, but you depend on their descriptions and behaviour.

Custom tools

Your own functions with @tool. You control the name, description, validation, errors and security. Most enterprise agents are mostly custom tools wrapping internal APIs.

Normal Python function call

You decide when and with which arguments: calculator("250*12"). Deterministic control flow.

Tool calling

The LLM decides when and with which arguments, based on the schema. Your runtime executes it and returns the result to the LLM. Arguments can be wrong, so validate them.

How does the LLM select a tool? It reads the schema

With @tool(parse_docstring=True), the function name, the docstring and the Args: section become the JSON schema below. This is all the LLM knows about your tool. Click a tool:

3.5

Advanced tool concepts

📐 Schema design

  • One clear job per tool, named with a verb: get_weather, not weather_util.
  • Use Literal[...] for fixed choices. It becomes an enum (see save_memory.category).
  • Keep the number of tools small (about 5–10). Large toolsets confuse small models.

✅ Input validation

  • Type hints are validated by Pydantic before your code runs. Invalid arguments go back to the model as an error automatically.
  • Validate business rules inside the tool (city exists, id format).
  • For complex inputs use @tool(args_schema=MyModel) with Field(..., ge=0).

🧯 Error handling

  • Expected errors: return "Error: …" so the model can recover.
  • Unexpected exceptions: @wrap_tool_call middleware turns them into a ToolMessage(status="error") (code below).

📜 Execution logging

  • A callback handler (AgentTracer) receives on_tool_start/on_tool_end/on_tool_error.
  • In production, send the same events to Langfuse or LangSmith (Module 6).

🔗 Sequential vs parallel calls

Parallel: independent tasks in one step (math + date). Sequential: step 2 needs step 1's result: "What's the weather where Priya's manager works?" → query_employee("Priya") → query_employee("Rahul") → get_weather("Bengaluru"), which takes three model calls.

🌐 External API integration

WEATHER_MODE=live calls the free Open-Meteo API (geocoding + forecast, no key). Add timeouts, fall back to cached data, and never let an API key appear in a tool's output.

from typing import Literal
from langchain.tools import tool

# sample rates for the lab (INR per 1 unit); use a rates API in production
_INR_PER = {"INR": 1.0, "USD": 84.0, "EUR": 91.0, "GBP": 107.0}
Currency = Literal["INR", "USD", "EUR", "GBP"]

@tool(parse_docstring=True)
def convert_currency(amount: float, from_currency: Currency, to_currency: Currency) -> str:
    """Convert an amount between INR, USD, EUR and GBP using the lab's sample rates.

    Args:
        amount: The amount to convert, e.g. 2500.
        from_currency: Currency code of the amount.
        to_currency: Currency code to convert to.
    """
    if from_currency not in _INR_PER or to_currency not in _INR_PER:
        return f"Error: unsupported currency pair {from_currency}->{to_currency}."
    result = amount * _INR_PER[from_currency] / _INR_PER[to_currency]
    return f"{amount:,.2f} {from_currency} = {result:,.2f} {to_currency} (sample rate)"

Module 4 · The most important module

Memory in AI Agents

⏱ 45 min

An LLM does not remember anything. Each call starts from zero, and the model only knows what is in that request. "Memory" means your application saves information and puts the right parts back into the next request.

4.1

Understanding memory

Stateless application

Each request is independent. "My name is Mahesh" → "What is my name?" → "I don't know." This is what build_agent("tools") does.

Stateful application

The app stores the conversation (and facts) and sends the relevant parts with every new request. The model looks like it remembers, but it is just reading its input.

Conversation history is the simplest memory: resend all previous messages each turn. It works until the context window fills up. Then cost and latency grow and older messages must be trimmed or summarised. Try it:

📏 Context window calculatorExactArithmetic on your inputs; real token counts depend on the tokenizer.

■ system + tools  ■ history  ■ does not fit

Short-term memory

The working memory of one conversation (thread): its messages and state. Gone when the thread ends, unless you persist it.

Long-term memory

Facts that matter across conversations: who the user is, preferences, past outcomes. Stored outside the thread and retrieved when relevant.

4.2

Types of agent memory

💬

1 · Short-term

Context during an ongoing conversation or agent thread.

"What did I just ask you?"
Tech: checkpointer + thread_id

🗄️

2 · Long-term

Important information across conversations and sessions.

Name, role, skills, interests.
Tech: Store + namespaces

🧭

3 · Agentic

Memory the agent manages itself: decides what to store, update, retrieve and how it changes future behaviour.

Task outcomes, feedback, lessons learned.
Tech: agent + Store + policies

🧭
Three mechanisms, three responsibilities

Short-term · conversation memory: "What did the user say earlier in this conversation?" → LangGraph checkpointer + thread_id.

Long-term · persistent user knowledge: "Which facts and preferences must still be there next session?" → LangGraph Store + SQLite, one namespace per user.

Agentic · memory management and learning: "What should the agent remember, retrieve, update or forget, and how should feedback change its next answer?" → memory tools + retrieval middleware + reflection + policy.

LangChain's documentation also uses cognitive-science terms. They describe what kind of information is remembered. They are conceptual categories, not three extra built-in LangGraph memory classes; all three are stored with the same Store API.

4.3

Short-term memory: LangGraph checkpointer

Agent state

The data that moves through the graph. For create_agent this is mainly messages (you can add fields with state_schema).

Thread

One conversation, identified by config={"configurable": {"thread_id": "s1"}}. Same id → same history.

Checkpointer

Saves a checkpoint (state snapshot) after every graph step and loads the latest one when you invoke the same thread again.

Implementations

InMemorySaver (dev, lost on exit) · SqliteSaver (single machine) · PostgresSaver (production).

⚠️ Common mistakes with short-term memory
  • No thread_id when a checkpointer is set: LangGraph raises an error that the checkpointer needs a thread_id in configurable.
  • Re-sending the whole history yourself while using a checkpointer: messages get duplicated. Send only the new message.
  • One thread for all users: users see each other's conversation. Use one thread per conversation, for example f"{user_id}:{session_id}".
  • Unbounded threads: long threads overflow the context window. Add SummarizationMiddleware or trim messages in @before_model.
4.4

Long-term memory: LangGraph Store

Short-term memory belongs to a thread. Start a new chat tomorrow and Aria has forgotten that you are a Data Scientist. A Store is a key-value document database that lives outside threads, organised like folders:

Namespace

A tuple path, usually per user: ("mahesh", "memories"). This gives isolation between users.

Key

The id inside a namespace: "role", "tech_stack". A stable key means an update overwrites the old value instead of adding a duplicate.

Value

A JSON dict: {"content": "User is a Data Scientist", "category": "profile", "version": 1, ...}

from langgraph.store.memory import InMemoryStore        # or SqliteStore / PostgresStore
store = InMemoryStore()
store.put(("mahesh", "memories"), "role", {"content": "User is a Data Scientist"})   # create / update
item = store.get(("mahesh", "memories"), "role")          # Item(namespace, key, value, created_at, updated_at)
items = store.search(("mahesh", "memories"), limit=10)    # list (semantic if the store has an index)
store.delete(("mahesh", "memories"), "role")

4.5

Agentic memory

In 4.4 the agent saved facts when it noticed them and searched only when it thought of it. Agentic memory makes memory a managed capability. The agent decides:

✅ What is worth remembering?

Durable, user-specific, useful later.

🚫 What to ignore?

Secrets, small talk, temporary states ("I'm tired right now").

♻️ When to update?

A new fact contradicts an old one → same key, new version.

🔎 When to retrieve?

Before every model call: inject relevant memories automatically.

🎓 Learn from experience

Feedback becomes "lessons"; each turn is logged as an episode.

🛟 Catch misses

A reflection step after the turn saves facts the agent forgot to save.

Semantic Memory with Embeddings, and Memory Governance

⏱ 15 min

Two questions every client will ask: "Will it find the memory if I phrase it differently?" (semantic search) and "What exactly does it store about my users, and who can see it?" (governance).

4B.1

Semantic memory with embeddings

1 · Embeddings

A model turns text into a list of numbers (a vector) so that texts with similar meaning get similar vectors. Same idea as the Day 1 RAG session, applied to memories.

2 · Memories → vectors

When a Store has an index, every store.put() embeds the content field and saves the vector next to the JSON value.

3 · Vector similarity

Cosine similarity = cos θ = (a·b) / (|a|·|b|). 1 = same direction (same meaning), 0 = unrelated.

4 · Keyword vs semantic

Keyword search matches words; it misses paraphrases and matches accidental words. Semantic search matches meaning, but needs an embedding model and can return weak matches.

5 · Top-K retrieval

Embed the query, rank memories by similarity, keep the best K (MEMORY_TOP_K), drop weak hits below a threshold.

6 · Inject into the agent

memory_injection calls search_memories(). It uses the vector index automatically when the Store has one, so no agent code changes.

Be honest about the policy

The memory policy in this lab is rule-based (regular expressions). It is good for teaching and as a first filter, but it is not a complete enterprise security control. Combine it with dedicated PII detection, access control, encryption, retention and human review.

Bind identity to conversation state

A subtle bug the review of this lab found: if the chat changes user but keeps the same thread_id, the checkpointer still holds the previous user's messages, and the new user sees them. main.py now scopes every thread to its user and starts a fresh thread on /user:

def scoped_thread_id(user_id: str, thread: str) -> str:
    """'mahesh:default' and 'priya:default' never share history."""
    return f"{user_id}:{thread}"

# main.py
answer, result = ask(agent, text, thread_id=scoped_thread_id(user, thread), user_id=user)
# /user priya  ->  user, thread = "priya", "default"   (new identity = new conversation)

In production, the user id comes from authentication and is bound to both the conversation state (thread id) and the storage namespace. Never accept it from the request body or from the model. Test: tests/test_agent.py::test_user_switch_never_shares_thread_history.

After the loop ends@after_agentreflect_and_log: episode + missed factsOnce per user turn (its own graph node)

When several middlewares use the same wrap hook, the first in the list is the outermost layer (it runs first on the way in and last on the way out). before_* hooks run in list order and after_* hooks in reverse order. Error handling has two layers: expected problems are returned by tools as "Error: …"; unexpected exceptions are caught by handle_tool_errors. Without that middleware, LangChain 1.x re-raises them and the run fails.

Where does the time go?

LLM calls dominate. Every extra tool round trip adds another model call, and the injected memory and tool schemas add input tokens to every call. To speed up: fewer, sharper tools; parallel tool calls; short memory blocks; a smaller or faster model for simple turns.

Evaluating responses and tool selection

Treat tool choice like a classifier: for each test question, compare the tools the agent called with the tools it should have called. Toggle the predictions:

📏 Tool-selection evaluatorExactPrecision, recall and exact-match are computed from the table.

What to evaluate

  • Tool selection: right tools, no unnecessary ones.
  • Arguments: expression, city correct.
  • Trajectory: order and number of steps.
  • Final answer: correct and grounded (LLM-as-a-judge, as in the Guardrails session).
  • Memory: right facts saved; nothing forbidden saved.

How

  • Offline: pytest with the mock (logic) + a small eval set run against the real model (behaviour).
  • Track pass rate per model and prompt version (Langfuse datasets / LangSmith experiments).
  • Re-run on every change to prompts, tool descriptions or the model.

🧪 Testing agents without an LLM

The 38 tests in tests/ run offline in under a second. conftest.py sets LLM_PROVIDER=mock and a temporary storage folder. The mock speaks the real tool-calling protocol, so the tests exercise the real graph, tools, checkpointer, store and middleware. Only the "reasoning" is scripted.

def test_long_term_memory_across_threads_and_agents(store):
    ask(build_agent("long_term", store=store), "I primarily work with Python and LangChain.",
        thread_id="s1", user_id="mahesh")
    fresh_agent = build_agent("long_term", store=store)          # new checkpointer = new session
    answer, result = ask(fresh_agent, "Suggest a project for me.", thread_id="s2", user_id="mahesh")
    assert "search_memory" in tools_called(result) and "AI Agent" in answer

Two kinds of tests

Logic tests (mock, every commit): tools, policy, persistence, wiring. Behaviour evals (real model, on prompt or model changes): does the model choose the right tools? scripts/m5_scenarios.py is a small behaviour eval. Run it with LLM_PROVIDER=ollama.

🚀 Toward production

Persistence

PostgresSaver + PostgresStore (with pgvector for semantic memory). One database, backups, multiple app replicas.

Privacy & governance

Memory policy + PII redaction (see the Guardrails session), user-visible "what do you remember?" and "forget me", TTL on memories (Store ttl=), audit fields (source, version).

Context management

SummarizationMiddleware for long threads; cap injected memories (MEMORY_TOP_K); summarise episodes into lessons periodically.

Safety for actions

HumanInTheLoopMiddleware for tools that change things (send email, update records); ToolCallLimitMiddleware / ModelCallLimitMiddleware against loops.

Serving

Wrap ask() in FastAPI (Day 1) and Docker Compose (Day 2); take user_id from authentication, not from the request body.

Quality loop

Langfuse/LangSmith traces → datasets of real conversations → evals on every prompt, tool or model change.
