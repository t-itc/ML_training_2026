Module 0 · Overview & Setup

⏱ 5 min
Objective

Connect this module to RAG Fundamentals and make sure every laptop can run the project.

Timing
  • 2 min — recap: documents → embeddings → cosine → top-K; what breaks at scale
  • 3 min — dataset tour (20 docs, 12 questions), run python -m pytest -q
Talking points
  • “Last time six sentences; today the problems real clients have: long documents, codes, synonyms, permissions, and proving improvements.”
  • No LangChain today on purpose — once you know the parts, any framework is just packaging.
Coding checkpoint
  • pytest passes (1 skipped).
  • Models were pre-cached with python -m app.main evaluate — do this before class; downloads take minutes.
Discussion questions
  • Which client RAG project of yours failed on retrieval rather than on the LLM?
Transition

“Retrieval can only find what chunking created.”

Module 1 · Document Chunking Strategies

⏱ 35 min
Objective

Choose a chunking strategy for a document type and explain the size/overlap/token trade-offs.

Timing
  • 8 min — why chunking matters; characters vs tokens; silent truncation
  • 12 min — seven strategies (expand each card; show the handbook examples)
  • 8 min — simulator: fixed vs recursive at 120 chars, then overlap, then structure and parent-child
  • 7 min — Python walkthrough (fixed + recursive walkers), run python -m app.main chunk
Demo instructions
  • Simulator: Method = Fixed, size 120 → find a sentence cut in half. Switch to Recursive. Turn on Compare.
  • Switch to Structure: point at the heading-path metadata under each card. Parent-child: one parent → several children.
  • Delete the headings in the textarea → structure-based shows the 'needs headings' message (PDF extraction often loses structure).
  • In Python, run the token-count snippet: show how VPN-417 splits into several tokens.
Discussion questions
  • What would you use for a 300-page PDF contract? For WhatsApp-style chat logs?
  • Why must the chunking configuration be versioned together with the index?
  • When is overlap a bad idea? (duplicates in top-K, cost)
Common misconceptions
  • “1 character ≈ 1 token” or a fixed ratio for all languages.
  • “Bigger chunks = more context = better retrieval.”
  • “Semantic chunking is always best” — it costs an embedding pass and needs tuning.
Coding checkpoint
  • python -m app.main chunk prints counts and min/avg/max per method; structure chunks show section metadata.
  • parent-child command prints a matched child and its parent.
Transition

“Chunks are the units we search — next, how they become vectors.”

Module 2 · Embedding Models

⏱ 35 min
Objective

Explain dense vs sparse, normalisation, asymmetric formats, and select an embedding model by criteria and evaluation.

Timing
  • 8 min — core terms table (stop on symmetric vs asymmetric and prefixes)
  • 10 min — model comparison table; filter Local/API/Multilingual; latency, cost, governance
  • 7 min — simulator: pick queries, click points, toggle normalisation
  • 10 min — Python: EmbeddingModel walker, embed and compare-models
Demo instructions
  • Simulator: “food abroad” query → FIN-003 top; uncheck Normalise and explain why raw dot products depend on length.
  • Run python -m app.main embed: show shape (6, 384), norms 1.0 and the tokenizer output.
  • Run compare-models --models minilm bge-small; read per-question lines, not only averages.
Discussion questions
  • A client has German and English documents and German users. Which families do you shortlist and how do you decide?
  • Data may not leave the network — what changes?
  • Two models both output 384 dims — can you mix their vectors?
Common misconceptions
  • “More dimensions = better.”
  • “Leaderboard #1 will be best for us.”
  • “Prefixes are optional decoration.”
  • “Cosine 0.8 = 80% relevant.”
Coding checkpoint
  • embed shows (6, 384) and row norms of 1.0.
  • compare-models prints a summary per model and the re-indexing reminder.
Notes
  • Specs in the table come from model cards / provider docs; check the links before quoting to a client — providers update models and pricing.
  • Learners with Ollama already have nomic-embed-text locally — a good bridge to the next session.
Transition

“Good vectors are half of retrieval. Now: different ways to search.”

Module 3 · Retrieval Methods

⏱ 40 min
Objective

Implement dense and BM25 retrieval, apply metadata filters and MMR, and explain multi-query, parent-child and contextual retrieval.

Timing
  • 12 min — ten method cards (spend most time on BM25, filters, MMR)
  • 5 min — architecture animation
  • 10 min — retrieval simulator
  • 13 min — Python: DenseRetriever walker, BM25/TF-IDF, filters, MMR walker, multi-query
Demo instructions
  • Simulator: WFH query → BM25 tokens work, home, policy; VPN-417 → BM25 exact; vacation → dense.
  • Set Department = HR with the VPN query: show how filters can hide the answer.
  • Python: search --method bm25 --query "What does error VPN-417 mean?"; then --department IT.
  • mmr: compare λ = 1.0 and 0.5 lists aloud.
  • If Ollama runs: multi-query; otherwise pass --variants.
Discussion questions
  • Where would you enforce document permissions — prompt, post-filter or pre-filter? Why?
  • Which questions in your client domain contain exact identifiers?
  • When could MMR hurt?
Common misconceptions
  • “BM25 is obsolete because we have embeddings.”
  • “Post-filtering is the same as pre-filtering.”
  • “Multi-query is free.” (LLM call + N searches)
Coding checkpoint
  • BM25 returns IT-004 first for the VPN-417 question.
  • --department IT returns only IT documents.
  • mmr prints two different lists.
Transition

“Dense and BM25 fail in different places — combine them.”

Module 4 · Hybrid Search & Reranking

⏱ 25 min
Objective

Fuse rankings with RRF and add a cross-encoder reranker; explain when reranking helps.

Timing
  • 5 min — WFH example: BM25 misses HR-003 (actual output), dense finds it
  • 7 min — RRF formula + widget (k = 60, k = 0, real WFH lists)
  • 5 min — bi-encoder vs cross-encoder, two-stage animation, rerank simulation
  • 8 min — Python: RRF and Reranker walkers, wfh-demo, rrf-demo
Demo instructions
  • RRF widget: ask why FIN-001 (in both lists) beats HR-003 (#2 in only one list) — agreement wins.
  • Run wfh-demo and read all four lists; then search --method rerank.
Discussion questions
  • What latency budget does your client have? How many candidates can you rerank in it?
  • When would you choose weighted score fusion over RRF?
  • The relevant chunk is #35 in hybrid — can the reranker help with top-20?
Common misconceptions
  • “RRF averages scores.” (ranks only)
  • “A reranker can find what retrieval missed.”
  • “Cross-encoder scores are probabilities.”
Coding checkpoint
  • rrf-demo: HR-001 = 1/(60+1) + 1/(60+2) = 0.03252.
  • wfh-demo: BM25 returns only HR-001; hybrid contains HR-001 and HR-003.
Transition

“Four pipelines — which is better for this client? Measure.”

Module 5 · Evaluation & Recap

⏱ 15 min
Objective

Compute P@K, R@K, MRR, nDCG and compare pipelines fairly on the same labelled data.

Timing
  • 4 min — metric table + calculator
  • 6 min — run python -m app.main evaluate, paste summary into the results table, discuss per-question differences
  • 5 min — final quiz + recap + checklist
Demo instructions
  • Calculator: mark ranks 2 and 4 relevant, total 2, K = 3 → explain each line of the calculation.
  • Evaluation table: BM25 row is a real computation in the browser and should equal the bm25 line from Python.
  • Stress that Dense/Hybrid rows in the browser are illustrative and look unrealistically good.
Discussion questions
  • How many labelled questions would you need for a client decision? Who labels them?
  • Which metric would you put on a dashboard for an HR assistant, and why?
  • A method wins on average but loses badly on legal questions — what do you recommend?
Common misconceptions
  • “One method is always better.”
  • “12 questions are enough to decide.”
  • “An unlabelled correct document is a retrieval error.”
Coding checkpoint
  • evaluate prints per-question ✓ marks and four summary lines; with --save it writes evaluation_results.json.
Transition

Next session: vector databases and ANN indexes, LLM generation with citations, end-to-end RAG evaluation.
